# Management Dashboard Analytics V1 — FE Agent Guide

> **Contract source:** backend source snapshot 2026-08-21.  
> **Audience:** Management/Backoffice FE, QA, and AI coding agents.  
> **Scope:** read-only operational dashboard. This is not a public Storefront API and does not replace the Order list/detail APIs.

## 1. What the page must show

```text
Management dashboard
├─ Report-period facts: orders, completed sales, payments/refunds, new users
├─ Current snapshots: pending fulfilment, catalog, producer, inventory, total users
└─ Breakdown: order status, payment method, time series, top products
```

The API intentionally mixes two kinds of facts:

| Group | Time meaning | Must change when the user changes `from/to`? |
| --- | --- | --- |
| `orders.kpis`, `orders.series`, `orders.statusBreakdown`, `orders.paymentMethodBreakdown`, `orders.topProducts` | Selected Vietnamese calendar-date range | Yes |
| `users.newRegisteredInPeriod` | Selected Vietnamese calendar-date range | Yes |
| `orders.currentPendingFulfillmentCount`, `catalog`, `producers`, `inventory`, `users.totalRegistered` | Current snapshot at request time | No |

Do not label a snapshot card as “trong kỳ”. In particular, `currentPendingFulfillmentCount` can include orders created before `from`.

## 2. Transport, authorization, and deployment boundary

Base URL: `/api/v1`.

```http
GET /api/v1/management/dashboard/overview
Authorization: Bearer <management-access-token>
Accept: application/json
```

This is a safe read request. The endpoint has no CSRF requirement and has no request body.

The authenticated user must hold **all** of these existing permission claims:

```text
orders.read
catalog.products.read
inventory.read
producers.read
user.read
```

The controller enforces authentication and `orders.read`; the handler enforces the remaining permissions too. Therefore, FE must treat any missing permission as unavailable dashboard access, even if its navigation/UI check accidentally exposes the page.

| HTTP status | Meaning | FE action |
| --- | --- | --- |
| `200` | Dashboard data was returned. Empty database is valid: counters are `0`, arrays are empty. | Render cards/charts. |
| `400` | Query is invalid. | Keep the current data; repair/reset the filter and show `details` / `validationErrors`. |
| `401` | No valid authenticated session/token. | Open login or refresh the authenticated session. |
| `403` | Authenticated, but missing at least one required permission. | Redirect to an access-denied state; do not retry. |
| `5xx` | Unexpected backend/database failure. | Show non-destructive retry UI; keep the last successful data marked stale. |

The code exists in the backend working tree. FE must call this endpoint only after this BE version is deployed; there is no legacy alias for the renamed pending field.

## 3. Query contract and date semantics

```http
GET /api/v1/management/dashboard/overview?from=2026-08-01&to=2026-08-31&granularity=Day&topLimit=10
```

| Query | Type / accepted values | Default | Rule |
| --- | --- | --- | --- |
| `from` | `YYYY-MM-DD` | 29 Vietnamese calendar days before today | Inclusive Vietnamese local date. |
| `to` | `YYYY-MM-DD` | Today in `Asia/Ho_Chi_Minh` | Inclusive Vietnamese local date. |
| `granularity` | `Day`, `Week`, `Month` | `Day` | Drives `orders.series` only. Send these exact enum values. |
| `topLimit` | integer `1`–`50` | `10` | Limits `orders.topProducts`. |

If neither date is supplied, the server returns a 30-day window including today. If only `to` is supplied, `from` is 29 days before that date. Internally the range is:

```text
[Vietnam from 00:00, Vietnam day after to 00:00)
```

So `from=2026-08-01&to=2026-08-31` includes every event from 1 August through 31 August in Vietnam, without requiring the FE to send a time or UTC offset.

Validation failures use these keys:

| Invalid case | `validationErrors` key |
| --- | --- |
| Unsupported `granularity` | `granularity` |
| `topLimit < 1` or `> 50` | `topLimit` |
| `from > to` | `from` |
| Inclusive date range is 367+ days | `range` |

## 4. Standard response envelope

All examples below show `data` inside the API envelope.

```ts
type ApiResponse<T> = {
  success: boolean;
  data: T | null;
  message: string | null;
  errorCode: string | null; // e.g. BAD_REQUEST, UNAUTHORIZED, FORBIDDEN
  validationErrors: Record<string, string[]> | null;
  details: string | null;
  timestamp: string; // UTC ISO-8601
};
```

On success, expect `success: true`, a non-null `data`, and `message: "Success"`. Do not parse business values from `message` or `details`.

## 5. Exact `data` mapping

```ts
type DashboardOverview = {
  currencyCode: "VND";
  timezone: "Asia/Ho_Chi_Minh";
  from: string;              // YYYY-MM-DD, normalized server range
  to: string;                // YYYY-MM-DD, normalized server range
  refreshedAtUtc: string;    // UTC ISO-8601; generated by the handler
  orders: DashboardOrders;
  catalog: DashboardCatalog;
  producers: DashboardProducers;
  inventory: DashboardInventory;
  users: DashboardUsers;
};

type DashboardOrders = {
  currentPendingFulfillmentCount: number;
  kpis: OrderKpis;
  series: OrderSeriesPoint[];
  statusBreakdown: OrderStatusBreakdown[];
  paymentMethodBreakdown: PaymentMethodBreakdown[];
  topProducts: TopProduct[];
};

type OrderKpis = {
  ordersPlaced: number;
  completedOrderCount: number;
  collectedGross: number;
  refundAmount: number;
  netCollected: number;
  completedSales: number;
};

type OrderSeriesPoint = {
  period: string; // YYYY-MM-DD; Day=date, Week=Monday, Month=first day of month
  ordersPlaced: number;
  completedOrderCount: number;
  collectedGross: number;
  refundAmount: number;
  netCollected: number;
  completedSales: number;
};

type OrderStatusBreakdown = {
  status: "Pending" | "Confirmed" | "Preparing" | "Shipping" | "Completed" | "Cancelled" | "DeliveryFailed";
  orderCount: number;
  grandTotalAmount: number;
};

type PaymentMethodBreakdown = {
  paymentMethod: "COD" | "BankTransfer" | "Gateway" | "SePay" | "SePayVietQr";
  collectedGross: number;
  refundAmount: number;
  netCollected: number;
};

type TopProduct = {
  productVariantId: string | null;
  productName: string;
  variantName: string;
  sku: string;
  quantitySold: number;
  salesAmount: number;
};

type DashboardCatalog = {
  totalProducts: number;
  draftProducts: number;
  reviewProducts: number;

  pausedProducts: number;
  discontinuedProducts: number;
  activeVariants: number;
  sellableActiveVariants: number;
  productsWithoutActiveVariant: number;
};

type DashboardProducers = {
  total: number;
  published: number;

};

```

The backend serializes enums as strings and property names as camelCase. Monetary and quantity values are JSON numbers. Use a decimal-safe presentation/formatting layer if the FE performs further money arithmetic; do not use a locally recomputed value as the displayed authority when the API already returns the derived value.

## 6. Business formulas — use these labels, not guesses

### 6.1 Order KPIs and charts

| Field | Server rule | Recommended FE label |
| --- | --- | --- |
| `ordersPlaced` | Order `PlacedAt` is in the report range. | Đơn đặt trong kỳ |
| `completedOrderCount` | An Order status-history transition to `Completed` happened in the range. | Đơn hoàn tất trong kỳ |
| `completedSales` | Sum of `GrandTotalAmount` for those completion transitions. | Doanh số đơn hoàn tất |
| `collectedGross` | `PaymentTransaction`: `status=Paid` and type `Capture` or `Verify`, by `OccurredAt` in range. | Tiền đã thu |
| `refundAmount` | `PaymentTransaction`: `status=Refunded` and type `Refund`, by `OccurredAt` in range. | Tiền đã hoàn |
| `netCollected` | `collectedGross - refundAmount`. | Thu ròng |
| `currentPendingFulfillmentCount` | Current Order status is `Pending`, `Confirmed`, `Preparing`, or `Shipping`; all time. | Đơn chờ xử lý hiện tại |

Important consequences:

- Completed orders and paid transactions are intentionally independent. Never derive one card from the other.
- A refund can occur in a different report period from the original payment.
- `statusBreakdown` groups orders **placed in the period** by their **current** status. It is not a historical status-transition funnel.
- `topProducts` includes `OrderItem` rows only for orders whose `Completed` transition is in the period. It is ordered by sales amount descending, then quantity descending, then SKU.
- No add-to-cart, search, page-view, checkout-funnel, or conversion metric is included in this API.

### 6.2 Series bucket behavior

The API always emits zero-valued buckets between the selected dates. Do not fabricate missing dates on the client.

| `granularity` | `period` represents | Example |
| --- | --- | --- |
| `Day` | Vietnamese calendar date | `2026-08-19` |
| `Week` | Monday of the containing Vietnamese week | `2026-08-17` |
| `Month` | First day of the containing Vietnamese month | `2026-08-01` |

For Week/Month, the `period` can be earlier than the selected `from` because it is the start of the bucket. The values still only include events inside the chosen report range. Parse `period` as a date-only Vietnam bucket key; do not parse it as a browser-local timestamp.

### 6.3 Catalog, producer, and inventory snapshots

| Field | Meaning / FE rule |
| --- | --- |
| `catalog.*Products` | Current Product counts by lifecycle status. The status counters should sum to `totalProducts`. |
| `activeVariants` | Current variants with `status=Active`, regardless of their Product status. Use for data-management health, not “for sale”. |
| `sellableActiveVariants` | Current `Active` variants whose Product is currently `Published`. Use this for KPI **“Biến thể đang bán”**. |
| `productsWithoutActiveVariant` | Current Products without any Active Variant. Useful for catalog completion/quality work. |
| `producers.unverified` | `total - verified`; it is not a separate pending-verification status. |
| `inventory.trackedVariantCount` | Current variants with `inventoryMode=Tracked`. |
| `stockedQuantity` / `reservedQuantity` / `incomingQuantity` | Sum across all non-deleted physical inventory levels for tracked variants. |
| `availableQuantity` | Server-derived `stockedQuantity - reservedQuantity`. Incoming stock is **not** sellable availability. |
| `outOfStockVariantCount` | Tracked variants where aggregated availability is `<= 0`; a tracked variant with no InventoryItem/InventoryLevel counts as available `0`, therefore out of stock. |
| `users.totalRegistered` | Current total user count only. |
| `users.newRegisteredInPeriod` | User `CreatedAt` inside the selected report range. No customer PII is returned. |

## 8. FE implementation requirements

1. Build a single dashboard query key from `from`, `to`, `granularity`, and `topLimit`; cancel or ignore stale in-flight requests when filters change.
2. Initialize filters with a local date string (`YYYY-MM-DD`), never `toISOString().slice(0, 10)` if browser timezone may shift the date.
3. Render `from`, `to`, `timezone`, and `refreshedAtUtc` in the page metadata. Format `refreshedAtUtc` for viewers in `Asia/Ho_Chi_Minh`.
4. Use `catalog.sellableActiveVariants` for the sales-ready KPI; retain `activeVariants` only for catalog operations/quality.
5. Map only `orders.currentPendingFulfillmentCount`. **Do not use or add fallback to `orders.pendingFulfillmentCount`; that field does not exist.**
6. Draw charts directly from `orders.series`, including zero buckets. For Week/Month, label the date as the bucket start, not an accidental browser-time conversion.
7. Show money using `currencyCode` (`VND` today), retain raw numeric values for chart scale, and do not calculate revenue from `ordersPlaced` or completion count.
8. On `401`/`403`, do not replace valid previous dashboard data with fake zero values. Navigate to login/access-denied or show the explicit state.
9. Do not expect email, phone, address, access token, guest token, payment provider reference, or other customer/payment PII in this response.

## 9. Minimal client example

```ts
export async function getManagementDashboard(
  params: { from?: string; to?: string; granularity?: "Day" | "Week" | "Month"; topLimit?: number },
  accessToken: string,
  signal?: AbortSignal
): Promise<ApiResponse<DashboardOverview>> {
  const query = new URLSearchParams();
  if (params.from) query.set("from", params.from);
  if (params.to) query.set("to", params.to);
  if (params.granularity) query.set("granularity", params.granularity);
  if (params.topLimit !== undefined) query.set("topLimit", String(params.topLimit));

  const response = await fetch(`/api/v1/management/dashboard/overview?${query}`, {
    method: "GET",
    credentials: "include",
    signal,
    headers: {
      Accept: "application/json",
      Authorization: `Bearer ${accessToken}`
    }
  });

  return response.json() as Promise<ApiResponse<DashboardOverview>>;
}
```

## 10. Related endpoint — do not use as the dashboard replacement

```http
GET /api/v1/management/orders/analytics/overview
```

This older Orders endpoint now shares the same period KPI/series/breakdown/top-product calculations and requires only `orders.read`. It returns only order analytics (`currencyCode`, `from`, `to`, `kpis`, `series`, `statusBreakdown`, `paymentMethodBreakdown`, `topProducts`); it does **not** return dashboard catalog/producer/inventory/user snapshots or `currentPendingFulfillmentCount`.

Use it for an Order analytics page that has only `orders.read`. Use `/management/dashboard/overview` for the combined Management dashboard after the five-permission gate is satisfied.

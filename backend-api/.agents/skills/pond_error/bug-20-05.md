# Bug Log 20/05 - Pond/Oxy Alert

Source of truth: source code at the current workspace state, then runtime logs.

This report records the 20/05 Oxy investigation and the current implementation status after the state-reset, offline reconciliation, batch-processing, and shutdown-outcome fixes.

## Superseded Follow-up - 2026-05-25

The historical Phase C state-recreation behavior documented below is no longer current. Notification timestamp persistence now requires the same active, unacknowledged `FirstFaultAt` incident and logs `OXY_NOTIFICATION_TIMESTAMP_SKIP` when state is missing or has moved on; it does not recreate an alert from a completed notification side effect.

## Latest Source Delta - 2026-05-26

- Code 300 telemetry is normalized to the final status per positive device id, persisted, and sent as one `HandleOxyStatusChangesCommand` batch. Two AirBlower failures in one input now evaluate once at final severity instead of issuing Normal then Critical initial notifications.
- Confirmed hub-offline health processing dispatches a batch every unhealthy interval. This lets confirmed input recreate a missing `OxiAlertState:{pondId}` / index entry without restoring state as a notification side effect.
- `TurnOffAllAsync` now returns `Dispatched` or `NoTarget`. `WarningHardwareSilencedAt` is written only after actual Bell/Speaker shutdown dispatch; `NoTarget` is retried after 60 seconds and thrown dispatch failures retry at the next worker tick.
- Reminder/escalation recipient resolution remains role-code-only. Active-account/role filtering is outside this incident fix scope.
- The escalation intent title touched by this patch now uses a correct Unicode value.

## Current Source Status - 2026-05-26

Current source has implemented the main fixes for the state-reset incident:

- `OxyAlertSessionState` has Redis-only fields:
  - `LastFaultTelemetryAt`
  - `RecoveryPendingAt`
  - `RecoveryPendingDeviceTimes`
  - `WarningHardwareSilencedAt`
  - `WarningHardwareSilenceRetryAfter`
- `OxyAlertConstants.RecoveryGraceSeconds = 120`.
- `HandleOxyStatusChangesCommandHandler` no longer removes `OxiAlertState:{pondId}` immediately when all failed devices temporarily recover. It marks recovery pending, persists state, keeps the pond indexed, and logs `OXY_RECOVERY_PENDING`.
- If FAULT returns during the recovery grace window, handler preserves the existing incident timeline and logs `OXY_STATE_RESET_PREVENTED`.
- Initial farmer notification timestamp persistence skips a missing or replaced incident and logs `OXY_NOTIFICATION_TIMESTAMP_SKIP`; it never recreates incident state from notification side effects.
- `OxyAlertQueueService` respects recovery grace and only clears state/index after confirmed recovery. It logs `OXY_RECOVERY_CONFIRMED_CLEAR`.
- `OxyAlertReminderService` checks `OxiAlertAck:{pondId}` before escalation and logs `OXY_ESCALATION_SKIP_ACK_MARKER`.

## OBS-2026-05-20-03: Acknowledge API long-running when warning hardware is slow

### Original Evidence

- API returned success but logged:
  - `Long Running Request: "AcknowledgeOxyAlertCommand" (5239 milliseconds)`
- Same trace had:
  - `[OxyAlertWorker] No Bell/Speaker devices found for Pond ...`

### Current Source Status

Status: known residual risk.

Correctness is protected because acknowledge sets and verifies `OxiAlertAck:{pondId}` first. Hardware shutoff remains best-effort after marker verification. If lock timeout happens after marker verification, API can still return success because telemetry suppression is already active.

The request can still be slow if `IOxyWarningHardwareService.TurnOffAllAsync` or WarningDevice resolution is slow. This is a latency/UX concern, not the current root cause of repeated notification.

### Follow-up Option

If acknowledge latency remains > 2-3 seconds often, consider moving warning-hardware shutoff to a background retry path after marker verification.

## BUG-2026-05-20-04: Oxy state deleted/recreated while fault is still active

### Original Evidence

- RedisInsight showed `OxiAlertState:{pondId}` appearing, disappearing, then reappearing while Oxy devices were still reporting FAULT.
- RedisInsight showed:
  - `Key with this name does not exist.`
- New state had reset timeline:
  - `startTime` reset
  - `firstFaultAt` reset
  - `lastFcmpushed=0001-01-01T00:00:00+00:00`
  - `farmerNotificationSentAt=0001-01-01T00:00:00+00:00`
  - `escalationNotificationSentAt=0001-01-01T00:00:00+00:00`
- Farmer received notifications around every 60s.
- Admin/manager did not receive escalation.

### Root Cause

The earlier source could remove `OxiAlertState:{pondId}` immediately when telemetry/reconcile saw `FailedDeviceIds.Count == 0`, even if that was only transient ON/recovery during flapping. When FAULT returned, the handler created a new incident state and reset `FirstFaultAt`, `LastFcmpushed`, and `FarmerNotificationSentAt`.

### Current Source Status

Status: fixed in source, pending runtime verification.

Current handler behavior:

- On temporary full recovery:
  - removes recovered device ids from state
  - if no failed devices remain, sets `IsActive=false`
  - sets `RecoveryPendingAt=now`
  - persists state for 1 day
  - keeps the pond in `OxiAlertPondsIndex`
  - logs `OXY_RECOVERY_PENDING`
- On FAULT returning during 120s grace:
  - sets `LastFaultTelemetryAt=now`
  - clears `RecoveryPendingAt`
  - reactivates state
  - preserves `FirstFaultAt` unless the recovery grace has expired
  - preserves `LastFcmpushed` and `FarmerNotificationSentAt`
  - logs `OXY_STATE_RESET_PREVENTED`

Current worker behavior:

- If state is inactive but still in recovery grace, it logs `OXY_RECOVERY_PENDING` and does not remove state/index.
- If reconcile finds no failed devices but `RecoveryPendingAt` or `LastFaultTelemetryAt` is still within grace, it persists inactive recovery state and logs `OXY_STATE_DELETED_TOO_EARLY`.
- It removes `OxiAlertState:{pondId}`, `OxiAlertAck:{pondId}`, and the pond id from `OxiAlertPondsIndex` only after confirmed recovery outside the grace window, logging `OXY_RECOVERY_CONFIRMED_CLEAR`.

### Runtime Verification Needed

Case: state stability under flapping.

- Clean Oxy keys for the pond.
- Trigger FAULT.
- Send ON/FAULT flapping for 2-3 minutes.
- Expect:
  - state does not disappear if FAULT returns within 120s
  - `FirstFaultAt` remains the original incident time
  - `LastFcmpushed` and `FarmerNotificationSentAt` are preserved after farmer notification
  - logs include `OXY_RECOVERY_PENDING` and `OXY_STATE_RESET_PREVENTED`
  - no repeated farmer initial notification every 60s for the same incident

Case: confirmed recovery.

- Trigger FAULT.
- Send recovery for all failed Oxy devices.
- Do not send FAULT again for more than 120s.
- Expect:
  - `OXY_RECOVERY_CONFIRMED_CLEAR`
  - `OxiAlertState:{pondId}` removed
  - `OxiAlertAck:{pondId}` removed
  - pond removed from `OxiAlertPondsIndex`

## BUG-2026-05-20-05: Admin escalation did not arrive after threshold

### Original Evidence

- Farmer received Oxy notifications from around 15:57.
- At 16:06 and 16:11 admin still had not received escalation.
- Runtime state showed:
  - `isActive=true`
  - `isAcknowledged=false`
  - `severity=2`
  - both failed device ids present
  - `lastFcmpushed=default`
  - `farmerNotificationSentAt=default`
  - `escalationNotificationSentAt=default`

### Current Source Status

Status: partially fixed in source, pending runtime verification.

Source fixes:

- `OxyAlertReminderService` chooses escalation baseline in this order:
  1. `FarmerNotificationSentAt`
  2. `LastFcmpushed`
  3. `FirstFaultAt`
  4. `StartTime`
- If fallback is used, it logs `OXY_ESCALATION_FALLBACK_BASELINE`.
- Threshold comparison logs include elapsed/required seconds.
- When the threshold is due, it logs `OXY_ESCALATION_ELIGIBILITY_DUE` before resolving pond and recipients.
- On publish, it logs `OXY_ESCALATION_PUBLISH`.
- After publish, it writes `EscalationNotificationSentAt` and verifies read-back.
- If ack marker exists, it skips and logs `OXY_ESCALATION_SKIP_ACK_MARKER`.
- Escalation recipient resolution returns users by the requested role codes; active-account/role filtering is intentionally outside this patch scope.
- Before publishing the DB notification event, escalation logs `OXY_ESCALATION_DB_NOTIFICATION_PUBLISH_INTENT` with pond id, recipient count, type, target URL, and title.
- `BulkNotificationEventHandler` logs empty-recipient events, insert intent, created DB notification count, and insert failures with notification type and target URL.

Remaining dependency:

- Admin escalation now depends on state stability. The state-reset fix should stop baseline reset, but runtime validation must confirm the same Redis instance, FCM recipients, and admin/manager tokens are valid.

### Runtime Verification Needed

- Clean Oxy keys.
- Trigger FAULT.
- Confirm farmer initial notification.
- Do not acknowledge.
- Wait `OxyAlert:EscalationAfterSeconds` in the active environment.
- Expect:
  - `OXY_ESCALATION_PUBLISH`
  - `RecipientCount > 0`
  - admin/manager/employee-manager notification appears
  - `EscalationNotificationSentAt` becomes non-default
  - no repeated escalation after it is set

If `OXY_ESCALATION_PUBLISH RecipientCount > 0` appears but mobile receives nothing, next investigation moves to FCM token/delivery, not Oxy state.

## Current Test Checklist

1. Initial FAULT, no ack:
   - expect state created
   - farmer initial notification sent
   - `FarmerNotificationSentAt` set after publish
2. Redis state missing after publish:
   - expect `OXY_NOTIFICATION_TIMESTAMP_SKIP`
   - expect no notification-side-effect state recreation
3. Flapping recovery/FAULT within 120s:
   - expect `OXY_RECOVERY_PENDING`
   - expect `OXY_STATE_RESET_PREVENTED`
   - state timeline preserved
4. Confirmed recovery after 120s with no FAULT:
   - expect `OXY_RECOVERY_CONFIRMED_CLEAR`
   - state/ack/index cleared
5. Ack then continued FAULT:
   - expect `OXY_ACK_SUPPRESS_ACTIVE_FAULT`
   - no farmer repeat
   - no admin escalation
6. No ack, wait threshold:
   - expect `OXY_ESCALATION_PUBLISH`
   - admin/manager recipients receive notification
7. One Code 300 input with two AirBlower faults:
   - expect one Critical initial notification and no prior Normal notification
8. Hub stays offline while Redis state is removed:
   - expect next health reconciliation batch recreates incident/index
9. Ack shutdown outcome:
   - `Dispatched` sets `WarningHardwareSilencedAt`
   - `NoTarget` leaves silenced unset and sets retry-after
   - thrown dispatch failure retries at next worker tick
